shtetl

Architecture, draft 4 of 2026-10-09. FreeBSD foundations, containers and systems kept on ZFS alone, with zfs_rebase in place of git. The details and the rulings are in docs/planning.md; docs/story.html walks one cycle frame by frame.

shtetl builds FreeBSD from source into foundations, runs containers (jails) and systems (bootable roots) as ZFS clones of them, saves each one as a delta, and carries each one onto a newer foundation with zfs_rebase. It follows mishkan and parasa. What is new is that the whole git layer is gone: no repositories inside trees, no mtree drift tracking, no two-commit save. A save is a snapshot carrying a commit message in shtetl:commit, and an incremental send; ZFS snapshots are the record, and git survives only as the way recipes are shared. An update stops the container and replays its saves, one rebase per dataset and snapshot, into a staging tree that takes its place until you cut over or abandon.

Four spaces

The user hands shtetl existing datasets at bootstrap; shtetl never touches devices. Each space has one root, which carries a shtetl:space user property, and its layout is there once, so every name has one place. A space is one dataset, and so one pool, which is what its clones and renames need. Layouts are created with the property defaults inherited from parasa (atime=off, compression=zstd, aclmode=passthrough, mountpoint=none, and canmount=noauto on the root itself, since ZFS never inherits canmount), each overridable in shtetl.conf.

Solid arrows move data; dashed arrows are configuration read. zlake is the authority for foundations, keeps one obj cache per foundation, and mirrors everything zrun runs as of its last save.

Datasets are the unit

zfs_rebase rebases one dataset per run: it reads each side through .zfs/snapshot, where a child dataset is only an empty directory, and refuses a mount nested inside the tree. So shtetl works dataset by dataset, and gives every dataset a lineage it can follow:

  • Foundation-inherited datasets. The foundation recipe's datasets are created empty in zlake/foundations/F before anything is installed. Every container and system dataset cloned from them has a base to rebase from.
  • Container-only datasets. A container recipe's own datasets (nginx's www) are created under the container on zrun; their lineage starts at the first save into zlake. A foundation update does not touch them, so the update clones them from the from-snapshot into the staging tree, and cutover promotes the clone so their history moves with them.
  • Placeholders. usr, which exists so that usr/local can mount at /usr/local, has canmount=off and holds nothing. zfs_rebase reads every side at its mountpoint, so a dataset that never mounts cannot be rebased; an update clones it from the new foundation instead, with -o canmount=off every time: a clone keeps none of its origin's properties, and a usr clone that mounts hides the tree's own /usr.
  • Everything is saved. Data included. There is no container-data or system-data tree: a container's datasets are its children, and zlake mirrors them the same way.

The version lives in the snapshot name, so a foundation is one dataset for its whole life: generic@15.2-releng-... follows generic@15.1-releng-... on the same chain, and a new release is an ordinary update, allowed or refused by the recipe's ver. Every snapshot carries its message in shtetl:commit and the config snapshot it was made with in shtetl:config; shtetl reads properties and never parses a name.

Three policies, each 0 (everything, the default), a bare number (the newest N) or a quoted date(1) interval ("7d"): retention.run (saves on zrun, and zlake's mirror keeps the same), retention.archive (retired trees), and update.depth (saves an update replays).

Lifecycle

Foundation

  1. Create zlake/foundations/F and its recipe datasets, empty.
  2. Mount F, foundation-builds/F and the src checkout; buildworld buildkernel with the obj tree on foundation-builds/F.
  3. On an update, delete-old delete-old-libs first, so installworld's closing certctl rehash sees only the new release's certificates. Then installworld installkernel distribution DESTDIR= the mounted F, every file with install -C; on an update, then installworld's own backups (*.old, init.bak) deleted.
  4. Foundation packages and commands; snapshot -r with the version name. Every version of F is one snapshot chain, which zfs_rebase and incremental send both need.
  5. Optionally shtetl pkg-upgrade F, a second snapshot ending in -pkg. Both are versions to rebase onto.

Container

  1. Send F@vN from zlake to zrun if zrun lacks it.
  2. Clone each dataset of F@vN under zrun/containers/X; create the recipe's own datasets.
  3. Start the jail; packages, then commands. Commands run once and never again on update, and a block the foundation already ran is not run again in the container.
  4. Save: snapshot with a message, then one send per dataset into the zlake mirror, as a clone of the zlake foundation where there is one.

Update a container onto F@v2

The recipe's ver must allow v2. shtetl stops X, which stays stopped as the rollback, takes a from-snapshot, and replays X's saves into the staging tree, oldest first and as many as update.depth allows, one zfs_rebase per inherited dataset and save, parent first. The first step finds its base from the origins; each later step names the previous save as its base, so a conflict answered once is not asked again. zfs_rebase reads every side at its own mountpoint, so shtetl mounts the zrun foundation read-only for the update, places each staging dataset before a later step takes it, and clones placeholders such as usr instead of rebasing them:

zfs_rebase --from zrun/containers/X/var@s1 \
    --onto zrun/foundations/F/var@v2 \
    --result zrun/containers/X-staging/var
zfs_rebase --allow-unrelated --base zrun/containers/X/var@s1 \
    --from zrun/containers/X/var@s2 \
    --onto zrun/containers/X-staging/var --result <name of s1>

Conflicts: the text first. A rebase that stops at its gate has already applied every clean action, and zfs_rebase merges nothing by itself. shtetl answers the derived files (pwd.db from master.passwd) keep, opens the picker with --continue -i --no-merge so the person merges the text while the gate stands, then regenerates the derived files from the merged sources and runs --continue. Derivations run only here. The step-by-step version is docs/story.html.

Soak. The results are placed at /containers/X-staging and started as a jail with X's own settings, address included: X is stopped, so nothing collides. The suffix is update.suffix in shtetl.conf. A pkg-upgrade during the soak adds a -pkg snapshot, so both states are there to pick from.

Cutover is a human decision, made after the soak. X has been stopped since the from-snapshot, so there is nothing to reconcile (if it was started again, shtetl says how much it wrote and asks). shtetl stops the staging jail, promotes the container-only clones, destroys the old tree on zrun, renames X-staging to X and starts it. In zlake the old X becomes archive/containers/X-<date>, kept whole by retention.archive. Abandon destroys the staging tree and starts X again as it was.

The lineage moves in zlake (a child keeping its incremental sends while its parent changes lineage, and promotes mirrored across pools) and the replay step's explicit base were tested on the box on 2026-10-11 and hold (planning.md 13.1, probes P1 - P3, P11 and P14).

System

The same as a container, deployed with zfs set -u mountpoint=/ and a one-shot boot; children mount at /var, /usr/local and so on by inheritance. A system is never updated while it runs: everything, cutover included, happens from outer space, a RAM root reached with reboot -r. The soak is a one-shot boot into the staging tree.

Configuration

All configuration is UCL, the format FreeBSD itself uses for pkg, ctld, bhyve and iovctl (read with textproc/libucl; base's copy is private). Each file is parsed strictly: no duplicate keys, no macros, no variables. shtetl.conf holds what is about the machine, and beside it the default recipe; a recipe is built from layers, nearest last:

layerfile
1the default: shtetl.conf, after what it imports
2recipes named in the target's import
3the target recipe

Everything stacks: a file adds to what the files below it gave, and nothing is dropped or replaced. Every collection (pkg, datasets, derivations, requires, commands, patches) is an object keyed by name, and their union is taken; texts (buildopts, jailconf, the lines of kernconf) are kept a piece from each file; every ver must hold. What one file gives, another does not give again, except a dataset's property, which may be overridden with a warning. The default is the one layer a recipe may override: it holds any kind's keys, and each recipe takes those of its kind. So a container ends with everything its foundation provides. A container recipe names no foundation; its ver says which ones it fits, and the foundation is chosen at shtetl create X --on F. See docs/ucl-primer.md.

Implementation

C, userspace, laid out like zfs_rebase: a portable core (config, cascade, planning) that builds and tests on the mac, and a FreeBSD layer on libzfs, libzfs_core and libjail. shtetl runs make, pkg, git, jail and zfs_rebase as child processes with argv arrays, never through a shell. FreeBSD 15.1 is the floor.

Gone since parasa

  • foundation.git, parasa.git, recipes.git on the data pool, and .git datasets inside trees
  • mtree baselines and drift classification prompts
  • the two-commit save, and pkg.list (packages are rebased with /usr/local)
  • replaying commands on update
  • container-data and system-data, and mount.fstab for a container's own datasets
  • disk partitioning, GELI and glabel at bootstrap
  • a DESTDIR or build workspace separate from the foundation, and an obj tree outside zlake
