shtetl

Architecture, draft 2 of 2026-10-08. FreeBSD foundations, containers and systems kept on ZFS alone, with zfs_rebase in place of git. The details, the rulings and the open questions are in docs/planning.md.

shtetl builds FreeBSD from source into foundations, runs containers (jails) and systems (bootable roots) as ZFS clones of them, saves each one as a delta, and carries each one onto a newer foundation with zfs_rebase. It follows mishkan and parasa. What is new is that the whole git layer is gone: no repositories inside trees, no mtree drift tracking, no two-commit save. A save is a snapshot carrying a commit message in shtetl:commit, and an incremental send; an update is one rebase per dataset into a staging tree that runs beside the old one until you cut over.

Four spaces

The user hands shtetl existing datasets at bootstrap; shtetl never touches devices. Each root carries a shtetl:space user property. zlake and zrun may have several roots, across pools: a child is looked for under every root of its space, and two matches is an error. An entity always lives in the root that holds its foundation, because a clone cannot cross pools. Layouts are created with the property defaults inherited from parasa (atime=off, compression=zstd, aclmode=passthrough, mountpoint=none, canmount=noauto), each overridable in shtetl.conf.

Solid arrows move data; dashed arrows are configuration read. zlake is the authority for foundations, keeps one obj cache per foundation, and mirrors everything zrun runs as of its last save.

Datasets are the unit

zfs_rebase rebases one dataset per run: it reads each side through .zfs/snapshot, where a child dataset is only an empty directory, and refuses a mount nested inside the tree. So shtetl works dataset by dataset, and gives every dataset a lineage it can follow:

  • Foundation-inherited datasets. The foundation recipe's datasets are created empty in zlake/foundations/F before anything is installed. Every container and system dataset cloned from them has a base to rebase from.
  • Container-only datasets. A container recipe's own datasets (nginx's www) are created under the container on zrun; their lineage starts at the first save into zlake. A foundation update does not touch them, so the update clones them from the from-snapshot into the staging tree, and cutover promotes the clone so their history moves with them.
  • Everything is saved. Data included. There is no container-data or system-data tree: a container's datasets are its children, and zlake mirrors them the same way.

Every snapshot carries its message in shtetl:commit. shtetl reads the properties and never parses a name. Retention is set per class in shtetl.conf: 0 keeps everything (the default), a bare number keeps that many newest saves, and a quoted date(1) interval such as "1y" prunes by age from cron.

Lifecycle

Foundation

  1. Create zlake/foundations/F and its recipe datasets, empty.
  2. Mount F, foundation-builds/F and the src checkout; buildworld buildkernel with the obj tree on foundation-builds/F.
  3. installworld installkernel distribution DESTDIR= the mounted F; on an update, then delete-old delete-old-libs.
  4. Foundation packages and commands; snapshot -r with the version name. Every version of F is one snapshot chain, which zfs_rebase and incremental send both need.
  5. Optionally shtetl pkg-upgrade F, a second snapshot ending in -pkg. Both are versions to rebase onto.

Container

  1. Send F@vN from zlake to zrun if zrun lacks it.
  2. Clone each dataset of F@vN under zrun/containers/X; create the recipe's own datasets.
  3. Start the jail; packages, then commands. Commands run once and never again on update.
  4. Save: snapshot with a message, then one send per dataset into the zlake mirror, as a clone of the zlake foundation where there is one.

Update a container onto F@v2

X may be running. shtetl takes a from-snapshot (warning that anything written after it will not be in the update), then runs one zfs_rebase per inherited dataset, parent first, into the staging tree:

zfs_rebase --from zrun/containers/X/var@<from> \
    --onto zrun/foundations/F/var@v2 \
    --result zrun/containers/X-staging/var

Conflicts. A rebase that stops at its gate has already applied every clean action. For each conflicted file that a recipe's derivations can regenerate (pwd.db from master.passwd), shtetl runs the derivation in the gated result and answers it keep; then it opens the picker with --continue -i for whatever is left. Derivations run only here.

Soak. The results are placed at /containers/X-staging and started as their own jail, beside the old X. The suffix is update.suffix in shtetl.conf. A pkg-upgrade during the soak adds a -pkg snapshot, so both states are there to pick from.

Cutover is a human decision, made after the soak. shtetl repeats the warning if X was written after the from-snapshot, stops both, saves X one last time, promotes the container-only clones, destroys the old tree on zrun, renames X-staging to X and starts it. In zlake the old X becomes archive/containers/X-<date>, kept whole, so anything it wrote after the from-snapshot can still be recovered. Abandon destroys the staging tree and leaves X as it was.

The lineage moves in zlake (a child keeping its incremental sends while its parent changes lineage, and promotes mirrored across pools) are the first things to test on the box (planning.md, probes P1 - P3 and P11) before this design is committed.

System

The same as a container, deployed with zfs set -u mountpoint=/ and a one-shot boot; children mount at /var, /usr/local and so on by inheritance. A system is never updated while it runs: the update runs from a RAM root after reboot -r, the soak is a one-shot boot into the staging tree, and the cutover runs from the RAM root again.

Configuration

All configuration is UCL, the format FreeBSD itself uses for pkg, ctld, bhyve and iovctl (read with textproc/libucl; base's copy is private). Each file is parsed strictly: no duplicate keys, no macros, no variables. shtetl.conf holds what is about the machine; a recipe is built from layers, nearest last:

layerfile
1built-in recipe defaults
2default.conf
3recipes named in the target's import
4the target recipe

Nearer layers replace scalars and merge objects. Every collection (pkg, datasets, derivations, requires, commands) is an object keyed by name, so a recipe adds an element by naming it, changes one by naming it with new fields, drops one with name = false, and drops everything inherited with reset. See docs/ucl-primer.md.

Implementation

C, userspace, laid out like zfs_rebase: a portable core (config, cascade, planning) that builds and tests on the mac, and a FreeBSD layer on libzfs, libzfs_core and libjail. shtetl runs make, pkg, git, jail and zfs_rebase as child processes with argv arrays, never through a shell. FreeBSD 15.1 is the floor.

Gone since parasa

  • foundation.git, parasa.git, recipes.git on the data pool, and .git datasets inside trees
  • mtree baselines and drift classification prompts
  • the two-commit save, and pkg.list (packages are rebased with /usr/local)
  • replaying commands on update
  • container-data and system-data, and mount.fstab for a container's own datasets
  • disk partitioning, GELI and glabel at bootstrap
  • a DESTDIR or build workspace separate from the foundation, and an obj tree outside zlake
