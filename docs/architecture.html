shtetl

Architecture, draft of 2026-10-04. FreeBSD foundations, containers and systems kept on ZFS alone, with zfs_rebase in place of git. The details and the open questions are in docs/planning.md.

shtetl builds FreeBSD from source into foundations, runs containers (jails) and systems (bootable roots) as ZFS clones of them, saves each one as a delta, and carries each one onto a newer foundation with zfs_rebase. It follows mishkan and parasa. What is new is that the whole git layer is gone: no repositories inside trees, no mtree drift tracking, no two-commit save. A save is a snapshot and an incremental send; an update is one rebase per dataset.

Four spaces

The user hands shtetl four existing pools or datasets at bootstrap. shtetl never touches devices. It marks each root with a shtetl:space user property (proposal) and builds its layout beneath, using the property defaults inherited from parasa (atime=off, compression=zstd, aclmode=passthrough, mountpoint=none, canmount=noauto), each overridable in shtetl.conf.

Solid arrows move data; dashed arrows are configuration read. zlake is the authority for foundations and holds the last save of everything zrun runs.

Datasets are the unit

zfs_rebase rebases one dataset per run: it reads each side through .zfs/snapshot, where a child dataset is only an empty directory, and refuses a mount nested inside the tree. So shtetl works dataset by dataset, and gives every dataset a lineage it can follow:

  • Foundation-inherited datasets. The foundation recipe's datasets are created empty in zlake/foundations/F before anything is installed. Every container and system dataset cloned from them has a base to rebase from.
  • Container-only datasets. A container recipe's own datasets (nginx's www) are created under the container on zrun. Their lineage starts at the first save into zlake. A foundation update does not touch them, so they are carried across, not rebased.
  • Everything is saved. Data included. There is no container-data or system-data tree: a container's datasets are its children, and so are their backups in zlake.

Lifecycle

Foundation

  1. Create zlake/foundations/F and its recipe datasets, empty.
  2. Mount F at a build path; buildworld buildkernel on zbuild.
  3. installworld installkernel distribution DESTDIR= the mounted F; on an update, then delete-old delete-old-libs.
  4. Foundation packages, commands, derivations.
  5. Unmount; zfs snapshot -r F@vN. Every version of F is one snapshot chain, which zfs_rebase and incremental send both need.

Container

  1. Send F@vN from zlake to zrun if zrun lacks it.
  2. Clone each dataset of F@vN under zrun/containers/X; create the recipe's own datasets.
  3. Start the jail; packages, commands, derivations.
  4. Save: snapshot -r, then one send per dataset into zlake/containers/X, as a clone of the zlake foundation where there is one.

Update a container onto F@v2

Save as @pre, then one zfs_rebase per inherited dataset, parent first, each into X-new:

zfs_rebase --from zrun/containers/X/var@pre \
    --onto zrun/foundations/F/var@v2 \
    --result zrun/containers/X-new/var
X
rebased onto F@v2; base F@v1 found from X's origin
X/usr-local
rebased onto F/usr-local@v2 (packages travel with it)
X/var
rebased onto F/var@v2 (logs and databases merged onto the new base var)
X/www
carried: zfs rename under X-new at finalize

Conflicts stop a rebase at its gate (exit 1) and shtetl opens the picker; any failure aborts every rebase the update started. Finalize stops the jail, checks written@pre, carries the container-only datasets, swaps X-new into place, sets mountpoints and readonly=off, restarts, and saves. The zlake copy is then re-homed as a clone of zlake/foundations/F@v2.

Re-homing in zlake, and whether a child's incremental sends survive its parent changing lineage, is the first thing to test on the box (planning.md, probes P1 - P3) before this design is committed.

System

The same as a container, deployed with zfs set -u mountpoint=/ and nextboot; children mount at /var, /usr/local and so on by inheritance. Finalize crosses a reboot.

Configuration

All configuration is UCL (textproc/libucl; base's copy is private). Each file is parsed strictly: no duplicate keys, no macros, no variables. shtetl owns the cascade:

layerfile
1built-in defaults
2zconfig/shtetl.conf
3zshtetl-recipes/default.conf
4recipes named in the target's import
5the target recipe

Nearer layers replace scalars, merge objects and append to lists. Recipe keys follow mishkan: ver, src_branch, kernconf, buildopts, datasets, pkg, commands, derivations, requires, jailconf. See docs/ucl-primer.md.

Implementation

C, userspace, laid out like zfs_rebase: a portable core (config, cascade, planning) that builds and tests on the mac, and a FreeBSD layer on libzfs, libzfs_core and libjail. shtetl runs make, pkg, git, jail and zfs_rebase as child processes with argv arrays, never through a shell. FreeBSD 15.1 is the floor.

Gone since parasa

  • foundation.git, parasa.git, recipes.git on the data pool, and .git datasets inside trees
  • mtree baselines and drift classification prompts
  • the two-commit save, and pkg.list (packages are rebased with /usr/local)
  • container-data and system-data, and mount.fstab for a container's own datasets
  • disk partitioning, GELI and glabel at bootstrap
  • a DESTDIR or build workspace separate from the foundation
