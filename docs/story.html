Act 0

The stage

One machine, kfar, with two pools: fast, an NVMe mirror it boots from, and tank, a raidz of large disks. Its admin installed shtetl and ran shtetl bootstrap, naming one existing dataset for each of the four spaces.

Frame 1

After bootstrap

Bootstrap touched no device. It set a local user property, shtetl:space, on each root, created the empty parents under zlake and zrun with parasa's defaults (atime=off, compression=zstd, aclmode=passthrough, mountpoint=none, canmount=noauto), and made zrun/containers the one parent that mounts by itself, at /containers.

zconfig is a clone of the zshtetl-recipes repo: default.conf came from upstream, shtetl.conf was written by bootstrap. zbuild is a FreeBSD src checkout the admin already had. From here on every frame shows the same four boxes; only what the story does changes.

How to read a frame: a dot before a name means mounted. Pills on the right are snapshots (blue a foundation version, grey a save, orange the snapshot an update starts from). A tinted row was created, written, read or removed in that frame, as the legend at the top says. Numbered arrows are the operations, listed under the diagram.

Act I

A foundation

A foundation is FreeBSD built from source by a recipe. Every container and system is a clone of one, so it is built first.

Frame 2

The admin writes a foundation recipe

The admin adds foundations/generic.conf to the recipes clone. It is three lines: everything else comes from default.conf, the base layer every recipe is built on. shtetl.conf is not part of any recipe; it holds what is about this machine.

foundations/generic.conf (new)
# foundations/generic.conf: a GENERIC kernel and world
ver = ">=15";
src_branch = "releng/15.1";
kernconf = "GENERIC";
default.conf
# default.conf: the base layer of every recipe (from upstream)

datasets {
    tmp {}
    var {}
    "usr/local" {}
}

derivations {
    "etc/passwd" {
        source = "etc/master.passwd";
        command = "pwd_mkdb -p -d /etc /etc/master.passwd";
    }
    "etc/pwd.db" {
        source = "etc/master.passwd";
        command = "pwd_mkdb -p -d /etc /etc/master.passwd";
    }
    "etc/spwd.db" {
        source = "etc/master.passwd";
        command = "pwd_mkdb -p -d /etc /etc/master.passwd";
    }
    "etc/login.conf.db" {
        source = "etc/login.conf";
        command = "cap_mkdb /etc/login.conf";
    }
}
shtetl.conf
# shtetl.conf: about this machine (bootstrap's starter)
update {
    suffix = "staging";
}
retention {
    run = 10;
    lake = 0;
    archive = "1y";
}
Open question Q-A

shtetl.conf and generic.conf are site files, which upstream's default .gitignore would ignore. An ignored file has no git history at all. Are zconfig's snapshots enough history for them, or should site files be committed in the local clone and only kept out of what is pushed upstream?

Frame 3

shtetl checks the recipe

shtetl build generic reads the recipe before it touches anything. The checks run in three rounds; any failure stops the command with the file and line.

parse (each file alone)
  • okdefault.conf, foundations/generic.conf: UCL, ASCII only
  • okno key written twice in one file (parsed with UCL_DUPLICATE_ERROR)
  • okno macros (.include, .priority, ...) and no $variables
schema
  • okevery key is known, and allowed for a foundation (kernconf yes; jailconf, requires, foundation no)
  • oktypes: ver and src_branch are strings; datasets and derivations are keyed collections
  • okdataset names are valid ZFS components; usr/local implies a placeholder usr
  • okevery derivation has a source and a command
meaning
  • okreleng/15.1 is version 15.1, branch type releng; it satisfies ver >= 15
  • okthe foundation name is generic-15.1-releng; no dataset of that name exists in any lake root, so this is a new foundation
  • okspaces: one root each for config, build, lake and run
  • okafter checkout: sys/amd64/conf/GENERIC exists in the src tree

What a failure looks like:

foundations/generic.conf:2: ver must be a string; write "15.10"
    (UCL read the float 15.1)
default.conf:1: macros are not allowed; use import
foundations/generic.conf:5: jailconf is a container key; a foundation
    cannot set it

Finding: usr/local is two datasets

Children mount by inheritance, and an inherited mountpoint is the parent's plus the child's name. A dataset called usr-local (parasa's name) would mount at .../usr-local, not /usr/local. So usr/local becomes usr with canmount=off, holding nothing, and usr/local under it, the way FreeBSD's own zroot does it. planning.md and the architecture page are corrected to match.

Frame 5

Pre-split: the datasets exist before any file does

shtetl creates the foundation and one child per recipe dataset, all empty, and an obj cache for this foundation.

Creating the children first is what makes everything later work. A container cloned from this foundation will have its own var, usr/local and tmp, each a clone of the foundation's, and so each one will have a base to rebase from when the foundation moves. A directory split into a dataset after the fact would have no such lineage.

Frame 6

Build

The src checkout, the obj cache and the foundation tree are mounted (the foundation's children follow by inheritance). The checkout moves to releng/15.1.

1 make buildworld buildkernel KERNCONF=GENERIC with MAKEOBJDIRPREFIX on foundation-builds/generic-15.1-releng. The obj tree stays there after the build, so the next build of this foundation starts warm (best with WITH_META_MODE).

Frame 7

Install into the foundation

There is no separate DESTDIR: the build installs straight into the mounted foundation.

2 make installworld installkernel distribution DESTDIR=the foundation's mountpoint. Files land in whichever dataset owns their path: /var in var, the /usr/local skeleton in usr/local, everything else (/usr included, since usr is a placeholder) in the foundation's own dataset. A foundation recipe with pkg or commands would run them now, in a chroot of the tree; this one has neither.

Frame 8

Snapshot: version v1

Everything is unmounted again and the foundation is snapshotted recursively, in one atomic step, with its properties set at creation.

zfs snapshot -r \
    -o shtetl:kind=version \
    -o shtetl:commit="build generic-15.1-releng from releng/15.1 0f691888dc56" \
    tank/shtetl/foundations/generic-15.1-releng@2026-10-08-0f691888dc56

From here on this page calls that snapshot v1. The name is for people ({recipe}-{ver}-{branch-type}, then @<ISO-date>-<short-sha>, so a listing sorts by recipe, version, then date); shtetl itself reads shtetl:kind. The foundation lives only in zlake so far. Nothing runs yet.

Act II

A container

The admin wants a web server: nginx, in a jail, on this foundation.

Frame 9

The container recipe, checked

containers/nginx.conf names its foundation, one package, one dataset of its own, one command block and its jail settings. shtetl create nginx checks it the same three ways, plus the checks that only make sense for a container.

containers/nginx.conf (new)
# containers/nginx.conf
foundation = "generic";

pkg = [ "nginx" ];

datasets {
    www {}
}

commands {
    nginx = <<EOD
sysrc nginx_enable=YES
EOD
}

jailconf = <<EOD
host.hostname = "nginx";
ip4.addr = "10.0.0.5";
EOD
container checks
  • okparse and schema as before; jailconf and foundation are container keys
  • okfoundation = "generic" names a recipe whose foundation exists: generic-15.1-releng, newest version v1
  • okrequires: none, so no other container must exist first
  • okdatasets: tmp, usr, usr/local, var exist in the foundation and will be clones; www is container-only
  • okderivation sources exist in v1 (etc/master.passwd, etc/login.conf)
  • okthe name nginx is free on zrun and in the zlake mirror
  • propa container recipe may not drop a dataset its foundation splits (tmp = false would leave /tmp a plain directory with nothing to rebase), nor a package its foundation installed: both are errors

             usr         from the foundation    (placeholder)

Finding: two keys the schema lacked

The plan's recipe keys had no way for a container to name its foundation; foundation is now in planning.md 5.5. The proposed rule above (no dropping what the foundation provides) is open question Q-F.

Frame 10

Bring the foundation to zrun

Clones cannot cross pools, so the foundation first goes where containers run.

1 One zfs send per dataset of v1, received under fast/shtetl/run/foundations with readonly=on and mountpoint=none. A full stream this first time; every later version goes as an incremental.

Frame 11

Clone, dataset by dataset

zfs clone is not recursive, so shtetl clones each dataset of v1 to the matching name under containers/nginx, then creates the recipe's own www.

1 zfs clone of each @v1. Nothing is copied: the clones share every block with the foundation until something writes. Mountpoints are inherited, so the tree mounts at /containers/nginx, /containers/nginx/var, and so on, with no fstab. www has no origin: its history will start at the first save.

Frame 12

Start the jail, install, run the commands

shtetl writes the jail's block to /etc/jail.conf.d/nginx.conf on the host, from the recipe's jailconf and the path, and starts it.

nginx {
    path = "/containers/nginx";
    host.hostname = "nginx";
    ip4.addr = "10.0.0.5";
    exec.start = "/bin/sh /etc/rc";
    exec.stop = "/bin/sh /etc/rc.shutdown";
}

service jail start nginx
pkg -j nginx install -y nginx            # usr/local, and var/db/pkg in var
jexec nginx /bin/sh -c 'sysrc nginx_enable=YES'   # etc/rc.conf in nginx

Commands run once, here, at creation. They never run again: an update carries what they did along with everything else.

Frame 13

Life happens

Weeks of ordinary administration. Each change lands in whichever dataset owns its path:

pw useradd ploni -m             etc/master.passwd etc/passwd etc/group
                                etc/pwd.db etc/spwd.db     -> nginx
vi /etc/ssh/sshd_config         PermitRootLogin no         -> nginx
vi /usr/local/etc/nginx/nginx.conf                         -> nginx/usr/local
site content                                               -> nginx/www
logs, pkg database                                         -> nginx/var

None of this is in any recipe, and none of it needs to be. There is no drift tracking and nothing to classify: the datasets are the record.

Frame 14

Save: s1

shtetl save nginx -m "site live, ploni added"

zfs snapshot -r -o shtetl:kind=save -o shtetl:commit="site live, ploni added" \
    fast/shtetl/run/containers/nginx@save-2026-10-09-101500

1 Each foundation-inherited dataset goes as a clone stream (zfs send -i <run foundation>@v1 nginx@s1) and is received in zlake as a clone of zlake's own foundation @v1, so zlake stores only what nginx changed. One arrow per kind is drawn; every dataset of the tree goes the same way. 2 www has no origin, so its first save is a full stream. From now on zlake mirrors nginx as of its last save: same names, same clone relationships, one pool over. Whether the clone streams land as clones without help is probe P1.

This snapshot is s1; its message travels in shtetl:commit (whether zfs send carries it is probe P10).

Act III

A new foundation version

Five weeks later FreeBSD publishes an errata notice for 15.1. The fix lands on releng/15.1. For this story, suppose it also changed /etc/ssh/sshd_config and added a system user to /etc/master.passwd and /etc/group: exactly the files the admin edited too.

Frame 15

Rebuild the same foundation

The admin runs the same command. Because generic-15.1-releng exists, this is an update of it, and there is one more check: the recipe's datasets must match the ones v1 has, because every container's datasets are clones of those.

$ shtetl build generic
foundation generic-15.1-releng, update: v1 -> @2026-11-12-5b2c7e01a9d4

  recipe   unchanged checks pass (parse, schema, meaning)
  datasets same as v1: tmp usr usr/local var (none added or dropped)
  src      fast/shtetl/src: pull releng/15.1 (0f691888dc56 -> 5b2c7e01a9d4)
  build    buildworld buildkernel, obj reused from foundation-builds
  install  into the same datasets, then delete-old delete-old-libs
  snapshot -r @2026-11-12-5b2c7e01a9d4  shtetl:kind=version

proceed? [y/N] y
Why the same datasets

Building v2 into the datasets v1 lives in keeps every version on one snapshot chain. zfs_rebase needs that to find a base, and zlake can then send zrun an incremental instead of a whole world.

Finding: a new release is a new foundation

If the recipe moved to releng/15.2, the name would become generic-15.2-releng: a new dataset with no lineage shared with 15.1, so no container could be rebased onto it. Moving between releases needs its own answer (perhaps building the new release into a clone of the old one's newest version). Not part of this story; it is open question Q-G.

Frame 16

Build and install over v1

The same mounts as before; the obj cache is already warm.

1 buildworld buildkernel, reusing the obj tree. 2 installworld installkernel distribution over v1, then make delete-old delete-old-libs DESTDIR=... to remove anything the new build no longer installs.

Known cost: installworld rewrites every file, so to zfs_rebase every file of the foundation looks changed between v1 and v2 and is decided on content. install -C leaves a byte-identical file untouched (FreeBSD already installs libraries that way); using it for everything would let the rebase skip unchanged files without reading them (probe P12).

Frame 17

Snapshot: version v2

@2026-11-12-5b2c7e01a9d4, called v2 from here on. zlake's foundation now carries both versions on one chain.

Frame 18

Send v2 to zrun

1 zfs send -i @v1 @v2 per dataset: only the blocks that changed. nginx is untouched; it is still a clone of @v1 and still running.

Act IV

The update

The admin moves nginx onto v2. Nothing in this act writes to the running nginx: the update is built beside it, tried, and only then swapped in, by the admin's decision.

Frame 19

Preflight

An update needs nothing from nginx but a snapshot to start from. nginx may be running, saved or not.

Frame 20

The from-snapshot: s2

zfs snapshot -r -o shtetl:kind=save \
    -o shtetl:commit="update to generic-15.1-releng@2026-11-12-5b2c7e01a9d4" \
    fast/shtetl/run/containers/nginx@save-2026-11-12-090000

An ordinary save snapshot, atomic across the whole tree, called s2 (orange: the update starts here). nginx keeps serving.

Frame 21

How zfs_rebase finds the base

shtetl names two snapshots and never the base. For the top dataset of the tree:

zfs_rebase --from fast/shtetl/run/containers/nginx@save-2026-11-12-090000 \
    --onto fast/shtetl/run/foundations/generic-15.1-releng@2026-11-12-5b2c7e01a9d4 \
    --result fast/shtetl/run/containers/nginx-staging

The tool walks each side's origin chain. From's: nginx@s2, then nginx's origin, generic-15.1-releng@v1, then that dataset. Onto's: generic-15.1-releng@v2, then that same dataset. The nearest dataset both descend from is the foundation, and of the two snapshots the walks name there, v1 and v2, the older is the base: v1. So the rebase replays everything nginx changed since v1 onto v2, and nothing else. This is why the pre-split in Act I mattered: nginx/var finds its base the same way, through generic-15.1-releng/var.

Frame 22

Rebase the top dataset

Parent first. zfs_rebase clones 1 onto (v2) as nginx-staging, read-only to the world and mounted only at its own private directory, and replays 2 from's changes (s2 against the base v1) into it.

Every clean action is applied first: the admin's nginx.conf, rc.conf line, home directory and so on, and every file the errata changed that the admin did not. Then the tool stops at its conflicts gate and exits 1. Six names were changed on both sides: etc/group, etc/master.passwd, etc/passwd, etc/pwd.db, etc/spwd.db, etc/ssh/sshd_config. The tool merges nothing by itself, however far apart the two edits are.

Frame 23

At the gate: the derived files step aside

The tool has written a resolution document beside its manifest: one line per conflicted name, each waiting for keep, onto or from. (Shown schematically; the grammar is v4-manifest.md section 8.)

the resolution, as the tool wrote it
#rebase-resolution 5
#base fast/shtetl/run/foundations/generic-15.1-releng@2026-10-08-0f691888dc56 ...
#from fast/shtetl/run/containers/nginx@save-2026-11-12-090000 ...
#onto fast/shtetl/run/foundations/generic-15.1-releng@2026-11-12-5b2c7e01a9d4 ...
#mode strict
#names 6
#unanswered 6
/
    etc/
        group conflict 1 -
        master.passwd conflict 2 -
        passwd conflict 3 -
        pwd.db conflict 4 -
        spwd.db conflict 5 -
        ssh/
            sshd_config conflict 6 -
            ..
        ..
    ..
after shtetl's pass
#unanswered 3
...
        group conflict 1 -
        master.passwd conflict 2 -
        passwd conflict 3 keep        <- derivation, regenerated later
        pwd.db conflict 4 keep        <- derivation, regenerated later
        spwd.db conflict 5 keep       <- derivation, regenerated later
        ...
            sshd_config conflict 6 -

shtetl matches the conflicted names against the recipe's derivations. passwd, pwd.db and spwd.db are all generated from master.passwd, so nobody should have to choose between two versions of them: shtetl answers them keep and remembers to regenerate them. But it cannot regenerate them yet, because their source is itself still in conflict.

Finding: the text has to be resolved first

A derived file almost never conflicts alone: whoever changed the binary changed its source too, and a source changed on both sides is itself a conflict, since zfs_rebase never merges text on its own. So the derivation can only run after the source has been merged. Today that takes two passes at the gate (this frame and the next two). With the merge drivers already designed in future-features.md, a headless text driver that accepts only conflict-free merges, followed by the derivation rules in the order written, would do it all before the picker opens.

Frame 24

At the gate: the admin merges the text

shtetl opens the picker and holds the rebase at the gate:

zfs_rebase --continue -i --no-merge fast/shtetl/run/containers/nginx-staging
 nginx-staging                          3 of 6 unanswered
   etc/group               conflict   -
   etc/master.passwd       conflict   -
   etc/passwd              conflict   keep
   etc/pwd.db              conflict   keep
   etc/spwd.db             conflict   keep
   etc/ssh/sshd_config     conflict   -

(a sketch of the list screen, not the tool's exact drawing)

etc/group and etc/master.passwd: the admin opens each into the merge screen. The errata added a system user near the top, the admin added ploni at the end; the three-way merge has no conflict chunk, so w writes the merged file into the tree and the line becomes keep.

etc/ssh/sshd_config: the errata rewrote the commented #PermitRootLogin default, the very line the admin had replaced with PermitRootLogin no. That is one conflict chunk; the admin picks their own side for it, the errata's other changes to the file come along as onto-only chunks, w writes, and the line becomes keep.

The picker exits. --no-merge means the gate stands even though the document is complete, which is what shtetl needs for the next step.

Frame 25

At the gate: regenerate, then finish

Now the source is merged in the tree, so the derivation can run. The three conflicted outputs share one command, so it runs once, in a chroot of the result's private mount:

chroot <private mount of nginx-staging> pwd_mkdb -p -d /etc /etc/master.passwd

zfs_rebase --continue fast/shtetl/run/containers/nginx-staging
    applying2 ... done, verified: exit 0

passwd, pwd.db and spwd.db now agree with the merged master.passwd, and their lines already say keep, which is exactly "leave what is in the tree". --continue applies the rest, runs the final check and reaches done. The tool hands the result back the way it always does: unmounted, read-only, mountpoint=none. Where it goes is shtetl's business, not the tool's.

Frame 26

The children, www, and placing the tree

1 The children rebase the same way, each into the matching name under nginx-staging: tmp, usr, usr/local and var (one drawn; each derives its own base through the foundation's matching dataset). None conflicts: the errata did not touch what nginx changed there, so each exits 0. Logs and the pkg database in var are replayed onto the new base's var.

2 www has no foundation counterpart and nothing in a foundation update touches it, so its whole "rebase" is zfs clone nginx/www@s2 nginx-staging/www.

Then shtetl places the tree (zfs inherit mountpoint, readonly=off) so it mounts at /containers/nginx-staging, and snapshots it with the version it now sits on: @2026-11-12-5b2c7e01a9d4 (v2, shtetl:kind=version). Whether a rebase may create its result under another rebase's result is probe P4.

Frame 27

Soak: old and new side by side

shtetl writes a jail block for nginx-staging and starts it. Both jails run. The admin tries the new one for as long as they like; a shtetl pkg-upgrade nginx-staging here would add a -pkg snapshot, so the plain and upgraded states would both be there to pick from.

Saving the staging tree mirrors it into zlake. 1 First nginx's from-snapshot s2 goes to zlake if it is not there yet (send -i s1 s2), because 3 the mirror of nginx-staging/www is a clone of zlake's nginx/www@s2, exactly as on zrun. 2 The rebased datasets go as clone streams of zlake's foundation @v2. The staging save is s3, "soak start".

Open question Q-C

Both jails want 10.0.0.5. How does the staging jail reach the network while the old one holds the address and ports: an address from a pool in shtetl.conf, its own vnet, or not started automatically?

Frame 28

Cutover on zrun

The soak went well. Cutover is the admin's decision, made by command.

$ shtetl cutover nginx
nginx was written after the update started (written@s2):
    nginx/var     1.4M     (logs)
    nginx/www       0
    nginx           0
These changes are not in nginx-staging. They will be kept in the archive.
cut over? [y/N] y

shtetl stops both jails. 1 A final save of the old nginx, s4, "final before cutover", goes to zlake, so the archive will hold what it wrote after s2. 2 zfs promote nginx-staging/www: the clone takes over www's snapshots up to s2, so the site's history moves with it, and the old www is left holding only s4 (probe P11). Then the old tree is destroyed on zrun; it lives on in zlake. 3 zfs rename nginx-staging nginx. Mountpoints follow by inheritance, so the new tree is now at /containers/nginx; the jail block is renamed and the jail started.

Frame 29

Cutover in zlake: the old mirror is archived
