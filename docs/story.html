Act 0

The stage

One machine, kfar, with two pools: fast, an NVMe mirror it boots from, and tank, a raidz of large disks. Its admin installed shtetl and ran shtetl bootstrap, naming one existing dataset for each of the four spaces.

Frame 1

After bootstrap

Bootstrap touched no device. It set a local user property, shtetl:space, on each root, created the empty parents under zlake and zrun with parasa's defaults (atime=off, compression=zstd, aclmode=passthrough, mountpoint=none, canmount=noauto), and made zrun/containers the one parent that mounts by itself, at /containers. zrun/foundations gets a real mountpoint, /shtetl/foundations, but nothing under it mounts by itself (canmount=noauto): zfs_rebase reads every side at its own mountpoint, so shtetl mounts a foundation there for the length of an update, and no longer.

zconfig is a clone of the shtetl-recipes repo: default.conf came from upstream, shtetl.conf was written by bootstrap. zbuild is a FreeBSD src checkout the admin already had. From here on every frame shows the same four boxes; only what the story does changes.

How to read a frame: a dot before a name means mounted. Pills on the right are snapshots (blue a foundation version, grey a save, orange the snapshot an update starts from). A tinted row was created, written, read or removed in that frame, as the legend at the top says. Numbered arrows are the operations, listed under the diagram.

Act I

A foundation

A foundation is FreeBSD built from source by a recipe. Every container and system is a clone of one, so it is built first.

Frame 2

The admin writes a foundation recipe

The admin adds foundations/generic.conf to the recipes clone. It is three lines: everything else comes from default.conf, the base layer every recipe is built on. shtetl.conf is not part of any recipe; it holds what is about this machine.

foundations/generic.conf (new)
# foundations/generic.conf: a GENERIC kernel and world
ver = ">=15";
src_branch = "releng/15.1";
kernconf = "GENERIC";
default.conf
# default.conf: the base layer of every recipe (from upstream)

datasets {
    tmp {}
    var {}
    "usr/local" {}
}

derivations {
    "etc/passwd" {
        source = "etc/master.passwd";
        command = "pwd_mkdb -p -d /etc /etc/master.passwd";
    }
    "etc/pwd.db" {
        source = "etc/master.passwd";
        command = "pwd_mkdb -p -d /etc /etc/master.passwd";
    }
    "etc/spwd.db" {
        source = "etc/master.passwd";
        command = "pwd_mkdb -p -d /etc /etc/master.passwd";
    }
    "etc/login.conf.db" {
        source = "etc/login.conf";
        command = "cap_mkdb /etc/login.conf";
    }
}
shtetl.conf
# shtetl.conf: about this machine (bootstrap's starter)
update {
    suffix = "staging";
}
retention {
    run = 10;
    lake = 0;
    archive = "1y";
}
ZFS is the record; git is for sharing

Upstream's .gitignore ignores everything upstream does not ship, so shtetl.conf and generic.conf stay local unless the admin shares one on purpose (git add -f). Their history is zconfig's snapshots, and every snapshot shtetl takes records the config snapshot it was made with. One hazard, tested: git overwrites ignored files without a word when a pull brings a file at the same path, so shtetl snapshots zconfig before any pull and refuses one that would collide.

Frame 3

shtetl checks the recipe

shtetl build generic reads the recipe before it touches anything. The checks run in three rounds; any failure stops the command with the file and line.

parse (each file alone)
  • okdefault.conf, foundations/generic.conf: UCL, ASCII only
  • okno key written twice in one file (parsed with UCL_DUPLICATE_ERROR)
  • okno macros (.include, .priority, ...) and no $variables
schema
  • okevery key is known, and allowed for a foundation (kernconf yes; jailconf, requires, foundation no)
  • oktypes: ver and src_branch are strings; datasets and derivations are keyed collections
  • okdataset names are valid ZFS components; usr/local implies a placeholder usr
  • okevery derivation has a source and a command
meaning
  • okreleng/15.1 is version 15.1, branch type releng; it satisfies ver >= 15
  • oka foundation is named after its recipe: generic; no dataset of that name exists in any lake root, so this is a new foundation
  • okspaces: one root each for config, build, lake and run
  • okafter checkout: sys/amd64/conf/GENERIC exists in the src tree

What a failure looks like:

foundations/generic.conf:2: ver must be a string; write "15.10"
    (UCL read the float 15.1)
default.conf:1: macros are not allowed; use import
foundations/generic.conf:5: jailconf is a container key; a foundation
    cannot set it

Finding: usr/local is two datasets

Children mount by inheritance, and an inherited mountpoint is the parent's plus the child's name. A dataset called usr-local (parasa's name) would mount at .../usr-local, not /usr/local. So usr/local becomes usr with canmount=off, holding nothing, and usr/local under it, the way FreeBSD's own zroot does it. planning.md and the architecture page are corrected to match.

Frame 5

Pre-split: the datasets exist before any file does

shtetl creates the foundation and one child per recipe dataset, all empty, and an obj cache for this foundation.

Creating the children first is what makes everything later work. A container cloned from this foundation will have its own var, usr/local and tmp, each a clone of the foundation's, and so each one will have a base to rebase from when the foundation moves. A directory split into a dataset after the fact would have no such lineage.

Frame 6

Build

The src checkout, the obj cache and the foundation tree are mounted (the foundation's children follow by inheritance). The checkout moves to releng/15.1.

1 make buildworld buildkernel KERNCONF=GENERIC with MAKEOBJDIRPREFIX on foundation-builds/generic. The obj tree stays there after the build, so the next build of this foundation starts warm (best with WITH_META_MODE).

Frame 7

Install into the foundation

There is no separate DESTDIR: the build installs straight into the mounted foundation.

2 make installworld installkernel distribution DESTDIR=the foundation's mountpoint, every file with install -C (it matters from v2 on). Files land in whichever dataset owns their path: /var in var, the /usr/local skeleton in usr/local, everything else (/usr included, since usr is a placeholder) in the foundation's own dataset. A foundation recipe with pkg or commands would run them now, in a chroot of the tree; this one has neither.

Frame 8

Snapshot: version v1

Everything is unmounted again and the foundation is snapshotted recursively, in one atomic step, with its properties set at creation.

zfs snapshot -r \
    -o shtetl:kind=version \
    -o shtetl:commit="build generic from releng/15.1 0f691888dc56" \
    -o shtetl:config=fast/shtetl/config@2026-10-08-140210 \
    tank/shtetl/foundations/generic@15.1-releng-2026-10-08-0f691888dc56

From here on this page calls that snapshot v1. The dataset is named after the recipe and the version is in the snapshot name, @{ver}-{branch-type}-{ISO-date}-{short-sha}, so a foundation is one dataset for its whole life: a later @15.2-releng-... continues the same chain. The names are for people; shtetl reads shtetl:kind, and shtetl:config points at the exact recipes this was built from. The foundation lives only in zlake so far. Nothing runs yet.

Act II

A container

The admin wants a web server: nginx, in a jail, on this foundation.

Frame 9

The container recipe, checked

containers/nginx.conf says which FreeBSD versions it fits, one package, one dataset of its own, one command block and its jail settings. It names no foundation: the admin picks one with shtetl create nginx --on generic, and shtetl checks the recipe the same three ways, plus the checks that only make sense for a container.

containers/nginx.conf (new)
# containers/nginx.conf
ver = ">=15";

pkg = [ "nginx" ];

datasets {
    www {}
}

commands {
    nginx = <<EOD
sysrc nginx_enable=YES
EOD
}

jailconf = <<EOD
host.hostname = "nginx";
ip4.addr = "10.0.0.5";
EOD
container checks
  • okparse and schema as before; jailconf is a container key
  • ok--on generic: the foundation exists, and its newest version, 15.1-releng-2026-10-08-0f691888dc56, satisfies ver >= 15
  • okrequires: none, so no other container must exist first
  • okdatasets: tmp, usr, usr/local, var exist in the foundation and will be clones; www is container-only
  • okderivation sources exist in v1 (etc/master.passwd, etc/login.conf)
  • okthe name nginx is free on zrun and in the zlake mirror
  • oknginx ends with a superset of what the foundation provides: lists are additive, and dropping a dataset the foundation splits (tmp = false) or a package it installed would be an error

Recipes are not tied to a foundation

A recipe says which versions it fits with ver and works on any foundation that satisfies it. The choice is made when the container is created, and the clone's origin records it from then on: no key, no file.

Frame 10

Bring the foundation to zrun

Clones cannot cross pools, so the foundation first goes where containers run.

1 One zfs send per dataset of v1, received under fast/shtetl/run/foundations with readonly=on and canmount=noauto. A full stream this first time; every later version goes as an incremental. The copy has a real mountpoint, /shtetl/foundations/generic, but is never mounted except while an update reads it: zfs_rebase reads every side at its own mountpoint and refuses one that is not mounted.

Frame 11

Clone, dataset by dataset

zfs clone is not recursive, so shtetl clones each dataset of v1 to the matching name under containers/nginx, then creates the recipe's own www.

1 zfs clone of each @v1. Nothing is copied: the clones share every block with the foundation until something writes. Mountpoints are inherited, so the tree mounts at /containers/nginx, /containers/nginx/var, and so on, with no fstab. usr, the placeholder, is cloned -o canmount=off: a clone keeps none of its origin's properties, and without it usr would mount over the tree's own /usr (P9). www has no origin: its history will start at the first save.

Frame 12

Start the jail, install, run the commands

shtetl writes the jail's block to /etc/jail.conf.d/nginx.conf on the host, from the recipe's jailconf and the path, and starts it.

nginx {
    path = "/containers/nginx";
    host.hostname = "nginx";
    ip4.addr = "10.0.0.5";
    exec.start = "/bin/sh /etc/rc";
    exec.stop = "/bin/sh /etc/rc.shutdown";
}

service jail start nginx
pkg -j nginx install -y nginx            # usr/local, and var/db/pkg in var
jexec nginx /bin/sh -c 'sysrc nginx_enable=YES'   # etc/rc.conf in nginx

Commands run once, here, at creation. They never run again: an update carries what they did along with everything else.

Frame 13

Life happens

Weeks of ordinary administration. Each change lands in whichever dataset owns its path:

pw useradd ploni -m             etc/master.passwd etc/passwd etc/group
                                etc/pwd.db etc/spwd.db     -> nginx
vi /etc/ssh/sshd_config         PermitRootLogin no         -> nginx
vi /usr/local/etc/nginx/nginx.conf                         -> nginx/usr/local
site content                                               -> nginx/www
logs, pkg database                                         -> nginx/var

None of this is in any recipe, and none of it needs to be. There is no drift tracking and nothing to classify: the datasets are the record.

Frame 14

Save: s1

shtetl save nginx -m "site live, ploni added"

zfs snapshot -r -o shtetl:kind=save -o shtetl:commit="site live, ploni added" \
    fast/shtetl/run/containers/nginx@save-2026-10-09-101500

1 Each foundation-inherited dataset goes as a clone stream (zfs send -i <run foundation>@v1 nginx@s1) and is received in zlake as a clone of zlake's own foundation @v1, so zlake stores only what nginx changed. One arrow per kind is drawn; every dataset of the tree goes the same way. 2 www has no origin, so its first save is a full stream. From now on zlake mirrors nginx as of its last save: same names, same clone relationships, one pool over. Whether the clone streams land as clones without help: they do (P1).

This snapshot is s1; its message is in shtetl:commit. The sends carry no properties (no -p, which would carry the dataset's local ones too), so after each receive shtetl copies the snapshot's shtetl:* properties onto zlake's copy (P10).

Act III

A new foundation version

Five weeks later FreeBSD publishes an errata notice for 15.1. The fix lands on releng/15.1. For this story, suppose it also changed /etc/ssh/sshd_config and added a system user to /etc/master.passwd and /etc/group: exactly the files the admin edited too.

Frame 15

Rebuild the same foundation

The admin runs the same command. Because generic exists, this is an update of it, and there is one more check: the recipe's datasets must match the ones v1 has, because every container's datasets are clones of those.

$ shtetl build generic
foundation generic, update: v1 -> @15.1-releng-2026-11-12-5b2c7e01a9d4

  recipe   unchanged checks pass (parse, schema, meaning)
  datasets same as v1: tmp usr usr/local var (none added or dropped)
  src      fast/shtetl/src: pull releng/15.1 (0f691888dc56 -> 5b2c7e01a9d4)
  build    buildworld buildkernel, obj reused from foundation-builds
  delete   delete-old delete-old-libs, the new tree's list
  install  into the same datasets, install -C
  cleanup  installworld's backups (*.old, init.bak)
  snapshot -r @15.1-releng-2026-11-12-5b2c7e01a9d4  shtetl:kind=version

proceed? [y/N] y
Why the same datasets

Building v2 into the datasets v1 lives in keeps every version on one snapshot chain. zfs_rebase needs that to find a base, and zlake can then send zrun an incremental instead of a whole world.

A new release is just a new version

Had the recipe moved to releng/15.2, the build would go into the same dataset and the version would be @15.2-releng-.... Installing a newer world over an older one and running delete-old is FreeBSD's own source-upgrade path, and every container keeps a lineage to rebase along; its recipe's ver decides whether it may follow.

Frame 16

Build and install over v1

The same mounts as before; the obj cache is already warm.

1 buildworld buildkernel, reusing the obj tree. 2 First make delete-old delete-old-libs DESTDIR=... with the new tree's list of obsolete files, then installworld installkernel distribution over v1, then installworld's own backups deleted. A live system deletes after installing, because it runs on its old files; a foundation runs nothing, and deleting first lets installworld's closing certctl rehash see only the new release's certificates (P6).

Every install uses install -C: a byte-identical file is left as it was, so the rebase can skip it without reading it. On a real world it cut the send from 1,010 MiB to 38 MiB (P12).

Frame 17

Snapshot: version v2

@15.1-releng-2026-11-12-5b2c7e01a9d4, called v2 from here on. zlake's foundation now carries both versions on one chain.

Frame 18

Send v2 to zrun

1 zfs send -i @v1 @v2 per dataset: only the blocks that changed. nginx is untouched; it is still a clone of @v1 and still running.

Act IV

The update

The admin moves nginx onto v2. nginx is stopped for the update and stays stopped until the admin cuts over or abandons: nothing writes to it, so the new tree cannot drift from it, and it is the rollback.

Frame 19

Preflight

The recipe's ver decides whether nginx may move to the target at all. This errata is still 15.1, so even a recipe pinned to "=15.1" would allow it; a 15.2 version would need a looser ver, which this one has.

Frame 20

Stop nginx, then snapshot: s2

service jail stop nginx
zfs snapshot -r -o shtetl:kind=save \
    -o shtetl:commit="update to generic@15.1-releng-2026-11-12-5b2c7e01a9d4" \
    -o shtetl:config=fast/shtetl/config@2026-11-12-090000 \
    fast/shtetl/run/containers/nginx@save-2026-11-12-090000

An ordinary save snapshot, atomic across the whole tree, called s2 (orange: the update starts here). Nothing has written to nginx since the stop, and nothing will until cutover or abandon.

Frame 21

Two saves, two steps, two bases

update.depth is 0 here, so the update keeps the whole history zrun holds: it replays s1, then s2, onto v2, one rebase per save and dataset. zfs_rebase moves one snapshot at a time, so this is how a container's saves survive an update.

stepfromontobaseresult
1nginx@s1generic@v2 generic@v1, found from the origins a new clone of v2, nginx-staging; snapshotted as s1'
2nginx@s2nginx-staging (the dataset)nginx@s1, named the same dataset, rebased in place; snapshotted as s2'

1 The first step names only from and onto. The tool walks each side's origin chain: nginx@s1, then nginx's origin generic@v1; generic@v2, the same dataset. Of the two snapshots the walks name there, the older is the base: v1. So step 1 replays everything nginx changed up to s1 onto v2, and that is where the conflicts are.

2 The second step names its base: s1. Left to derive it, the tool would find v1, the divergence point, again (both origins still meet at the foundation). But onto is now the result so far, which already holds s1: with base v1, a file the admin edited both before s1 and before s2 would look changed on both sides and conflict, and every conflict answered in step 1 would come back, since from still holds the admin's version, onto the merged one, and both differ from v1. With base s1, only what the admin changed between s1 and s2 is replayed, the way git replays each commit against its own parent. Naming a base takes --allow-unrelated today, which turns the tool's prune off, so this step reads every file; the box suite has run that flag only as a dry run so far. Probe P14 measures it, and the numbers decide whether zfs_rebase should learn to prune from's side when the base is an earlier snapshot of from's own dataset (planning.md 7.6.2; ruled: not now).

Frame 22

Step 1, the top dataset: s1 onto v2

First shtetl mounts the foundation's datasets on zrun, read-only, at /shtetl/foundations/generic: zfs_rebase reads base, from and onto at their own mountpoints. Then, parent first, zfs_rebase clones 1 onto (v2) as nginx-staging, mounted only at its own private directory, and replays 2 from's changes (s1 against the base v1) into it.

zfs_rebase --from fast/shtetl/run/containers/nginx@save-2026-10-09-101500 \
    --onto fast/shtetl/run/foundations/generic@15.1-releng-2026-11-12-5b2c7e01a9d4 \
    --result fast/shtetl/run/containers/nginx-staging

Every clean action is applied first: the admin's nginx.conf, rc.conf line, home directory and so on, and every file the errata changed that the admin did not. Then the tool stops at its conflicts gate and exits 1. Six names were changed on both sides: etc/group, etc/master.passwd, etc/passwd, etc/pwd.db, etc/spwd.db, etc/ssh/sshd_config. The tool merges nothing by itself, however far apart the two edits are.

Frame 23

The tool has written a resolution document beside its manifest: one line per conflicted name, each waiting for keep, onto or from. (Shown schematically; the grammar is v4-manifest.md section 8.)

shtetl matches the conflicted names against the recipe's derivations. passwd, pwd.db and spwd.db are all generated from master.passwd, so nobody should have to choose between two versions of them: shtetl answers them keep and remembers to regenerate them. It cannot regenerate them yet, because their source is itself still in conflict.

The text first (ruled 2026-10-08)

A derived file almost never conflicts alone: whoever changed the binary changed its source too, and a source changed on both sides is itself a conflict, since zfs_rebase never merges text on its own. So the derivation runs after the source has been merged: two passes at the gate, this frame and the next two. zfs_rebase's planned merge drivers (future-features.md) would do it headless whenever the text merges cleanly, given rules that run in the order written.

Frame 24

At the gate: the admin merges the text

shtetl opens the picker and holds the rebase at the gate:

zfs_rebase --continue -i --no-merge fast/shtetl/run/containers/nginx-staging
 nginx-staging                          3 of 6 unanswered
   etc/group               conflict   -
   etc/master.passwd       conflict   -
   etc/passwd              conflict   keep
   etc/pwd.db              conflict   keep
   etc/spwd.db             conflict   keep
   etc/ssh/sshd_config     conflict   -

(a sketch of the list screen, not the tool's exact drawing)

etc/group and etc/master.passwd: the admin opens each into the merge screen. The errata added a system user near the top, the admin added ploni at the end; the three-way merge has no conflict chunk, so w writes the merged file into the tree and the line becomes keep.

etc/ssh/sshd_config: the errata rewrote the commented #PermitRootLogin default, the very line the admin had replaced with PermitRootLogin no. That is one conflict chunk; the admin picks their own side for it, the errata's other changes to the file come along as onto-only chunks, w writes, and the line becomes keep.

The picker exits. --no-merge means the gate stands even though the document is complete, which is what shtetl needs for the next step.

Frame 25

At the gate: regenerate, then finish

Now the source is merged in the tree, so the derivation can run. The three conflicted outputs share one command, so it runs once, in a chroot of the result's private mount:

chroot <private mount of nginx-staging> pwd_mkdb -p -d /etc /etc/master.passwd

zfs_rebase --continue fast/shtetl/run/containers/nginx-staging
    applying2 ... done, verified: exit 0

passwd, pwd.db and spwd.db now agree with the merged master.passwd, and their lines already say keep, which is exactly "leave what is in the tree". --continue applies the rest, runs the final check and reaches done: nginx-staging now holds s1's tree on v2. The tool hands it back unmounted, read-only, mountpoint=none, and shtetl places it at once (zfs inherit mountpoint, readonly=off): step 2 takes it as a dataset, and the dataset form takes only a mounted one.

Frame 27

The children, www, and starting the new tree

1 Each child replays the same two steps into the matching name under nginx-staging: tmp, usr/local and var (one drawn), each placed after its step 1 so that step 2 can take it. Step 1 finds each child's base through the foundation's matching dataset; step 2 names the child's own s1. None conflicts. var's logs and pkg database land on the new base's var.

3 usr is a placeholder with canmount=off: never mounted, so it can never be a rebase's side, and it holds nothing anyway. shtetl clones it from generic/usr@v2, -o canmount=off, before usr/local's result is created under it.

2 www has no foundation counterpart and nothing in a foundation update touches it, so it is never replayed: its whole "rebase" is zfs clone nginx/www@s2 nginx-staging/www.

Then shtetl unmounts the foundation's datasets, snapshots the tree, mounted at /containers/nginx-staging, with the version it now sits on (v2, shtetl:kind=version), and starts it as a jail with nginx's own settings, address included: nginx is stopped, so nothing collides. The order matters: each dataset's whole replay finishes before any child of it is made, because zfs_rebase refuses a step on a parent while a child is mounted below it (P4).

Frame 28

Soak

nginx-staging serves; nginx sits stopped and untouched. The admin tries the new tree for as long as they like. If it misbehaves, shtetl abandon nginx stops and destroys the staging tree and starts nginx again exactly as it was. A shtetl pkg-upgrade nginx-staging here would add a -pkg snapshot, so the plain and upgraded states would both be there to pick from.

Saving the staging tree, s3 "soak start", mirrors it into zlake. 1 First nginx's s2 goes to zlake if it is not there yet (send -i s1 s2), because 3 the mirror of nginx-staging/www is a clone of zlake's nginx/www@s2, exactly as on zrun. 2 The replayed datasets go as clone streams of zlake's foundation @v2, carrying s1', s2' and v2 with them (send -I).

Frame 29

Cutover on zrun

The soak went well. Cutover is the admin's decision, made by command. nginx has been stopped since s2, so there is nothing to reconcile; had the admin started it again during the soak, shtetl would say how much it wrote and ask.

$ shtetl cutover nginx
nginx has not been written since the update started (written@s2 = 0).
cut over to nginx-staging? [y/N] y

shtetl stops the staging jail. 1 zfs promote nginx-staging/www: the clone takes over www's snapshots up to s2, so the site's history moves with it (probe P11). Then the old tree is destroyed on zrun; it lives on in zlake. 2 zfs rename nginx-staging nginx. Mountpoints follow by inheritance, so the new tree is now at /containers/nginx; the jail block is renamed and the jail started.

Frame 30

Cutover in zlake: the old mirror is archived

zlake follows, so its mirror matches zrun again. First the same promote of www in the mirror, so zlake's nginx-staging/www now carries s1 and s2 as well.

1 zfs rename of the old mirror to archive/containers/nginx-2026-11-20. Same pool, so it is a rename and copies nothing. The archive keeps the old tree whole, on v1 with s1 and s2, until retention.archive (one year here) prunes it.

Frame 31

Cutover in zlake: the staging mirror becomes nginx

1 zfs rename of containers/nginx-staging to containers/nginx, matching zrun. zlake's nginx is now a clone of zlake's foundation @v2 carrying s1' and s2', and its www carries the site's whole history.

Drawn as done, and proven on the box

These moves rest on ZFS behaviour: a clone stream lands as a clone (P1), a child keeps receiving incremental sends after its parent changes lineage or name (P2), and a promote can be mirrored across pools (P11). The box confirmed all three on 2026-10-11.

Frame 32

Where everything stands

The end of one cycle. nginx runs on v2 with everything the admin did, merged with everything the errata did, and with its history: s1 and s2 replayed as s1' and s2'. 1 Its first save after cutover, s5, "cut over", goes to the renamed mirror as an ordinary incremental.

The next errata, or the next release, starts again at Act III: build into the same foundation, send the increment, stop, replay into staging, soak, cut over. Nothing in the cycle needed git beyond sharing recipes, and nothing was written into a running tree except by the admin and by the jail's own pkg and commands at creation.

Three policies decide how much of this is kept

retention.run: the saves on zrun, and zlake's mirror keeps the same. retention.archive: the retired trees. update.depth: how many saves an update replays, never more than zrun keeps. Each is 0 (everything), a number, or a quoted interval such as "7d".
